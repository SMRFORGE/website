How trust is built

Five steps. Each one ends in an artifact you can check.

Accuracy claims are universal. SMRFORGE ships, with every result, the process that would catch a wrong number — and the record that lets an independent reviewer confirm it without taking our word for anything.

1

Fidelity declaration

Every result carries a machine-readable fidelity label — screening, reference, or lab-escalation — stated in the output record itself.

2

Residual quantification

Validation is reported per benchmark with published bands — e.g. the CE Monte Carlo's characterized +320 pcm residual vs OpenMC (bounded, temperature-consistent) and the IAEA-2D full-core closure to ≈ −3 pcm — with every anchor and open item in the public V&V matrix.

3

Cryptographic sealing

Each run is committed to a tamper-evident bundle — a SHA-256 manifest of every input, output, and software version; any alteration breaks the seal.

4

Data & derivation provenance

A result pins, in the signed record, a content fingerprint of the nuclear data it read — so a reviewer can confirm which data produced a number (a run that pins none is honestly marked unpinned, never a fabricated claim). A composed result also carries its derivation lineage: the ordered sub-calculations it was built from, each with input/output digests. Edit either and the seal breaks.

5

Independent verification

A standalone verifier confirms a record's integrity — unedited, and consistent with the open Evidence Envelope schema — offline, with any conformant verifier, including one you implement yourself.

Verified and characterized, closure-by-closure — error bars published

We state each closure with its published band — and we publish where the methods don't agree, too.

An honest starting point: there are almost no measured SMR benchmarks yet — most SMRs aren't operating — so, like the whole field, we anchor the method to the best-characterized data that exists, and we characterize the engine against a reference code (OpenMC). On real ENDF/B-VIII.0 data our continuous-energy Monte Carlo reproduces OpenMC to a small, positive, bounded ≈ +320 pcm residual (band +205…+429), and — the decisive evidence it's a consistent engine, not a tuned one — that residual is flat with temperature and tracks U-238 content. Code-verification anchors hold tightly too: the IAEA-2D full-core closure lands at ≈ −3 pcm vs the published 2-D reference, cross-checked FD-vs-NEM. Then — the part that matters for your SMR — the same inputs escalate to OpenMC, free for everyone, so you get a code-to-code check on your actual design. These are method and code-verification anchors, not SMR-specific validation — and we say so. Every result is a bundle you re-verify offline; what Pro adds is the assurance layer that turns the numbers into a regulatory submission.

Built for simulations you can defend

Reproducibility is the product, not a feature.

Every k-eff calc, every benchmark, every report ships as a verifiable evidence bundle. A SHA-256 manifest of inputs and outputs. A reproducibility block — engine and code version, the data library it read and its content digest (the bundled few-group set for a screening k-eff, an ENDF-derived pack for the continuous-energy path), the RNG seed, and a determinism statement, plus an unsigned host diagnostic (Python version, platform) outside the seal. And, for a composed result, its derivation lineage — the ordered sub-calculations it was built from, each with input/output digests — all inside the signed record.

Hand the bundle to a colleague, a reviewer, or a regulator. They run a standalone verifier offline and either confirm the record's integrity — unedited and schema-valid — or refute it, checked against the open, independently-implementable Evidence Envelope schema (a versioned spec, JSON Schema, and conformance vectors), not a SMRFORGE-proprietary format. No "trust me, it ran on my machine." (Re-running the physics end-to-end is a separate, deeper check: smrforge reproduce <bundle> re-runs the open engine on the bundle's own recorded inputs and checks the numbers re-derive — the certify_bundle / reproduce_bundle Python API is the same path. A stochastic result — a Monte Carlo k-eff — can't re-derive to the last digit, so its record carries a statistical reproduce_tolerance: an n-sigma band built from the run's own reported uncertainty, and reproduce accepts a re-run that lands inside it. That tolerance rides inside the seal, so it can't be quietly widened to wave a bad number through — loosen it and the seal breaks. This is concrete for the lab tier: a real OpenMC criticality result now ships as a reproducible bundle — a reviewer installs OpenMC, re-runs it on the record's own inputs, and watches the k re-derive within that band (reviewer guide; honestly scoped — a multi-group eigenvalue, code-to-code against OpenMC, not a measured-reactor validation).) The published conformance vectors let you certify any verifier — ours or one you wrote yourself — so "independently-implementable" is something you prove, not something we ask you to take on faith.

Evidence bundles

Versioned, hashable, schema-checked. The same evidence plumbing internally is what regulators and reviewers receive — no separate export pipeline to maintain.

Pure Python standard library, zero dependencies, zero CDN fetches at runtime. Works on a laptop with no internet, in a SCIF, or behind an enterprise firewall. Locked surface, gated drift

A full behavior test suite, published conformance vectors, and signed reproduce-demo bundles — run them yourself against any build. A determinism check guards bit-reproducibility. Blocking CI runs ruff and the fast behavior suite on every change; the slow Monte-Carlo/transport and OpenMC tests run separately. The same checks are yours to run.

Which data produced it

A result pins, in the signed record, a content fingerprint of the nuclear data it read — so a reviewer confirms which data set produced a number, and re-derives that fingerprint from their own copy of the data (a run that pins none is honestly marked unpinned). Change a constant and the fingerprint changes; edit the claim and the seal breaks. (Proof that a bundle existed at a point in time will use a commodity timestamp when a customer needs it.)

One gateway, every surface

API + AI tools — one process you can audit.

The SMRFORGE gateway is a single stdlib HTTP surface — no web framework — that fronts the REST API and the MCP tool catalog your AI agents can call. One process, one port, one OpenAPI spec, one surface to inspect. Today it is a Python API (smrf_serve) you start in-process; a serve console command is on the roadmap.

The point of putting reactor physics behind MCP isn't just access — it's that an agent calls a tool and gets back a signed evidence record, not a bare number, so it can verify and reproduce the result before it trusts it. A runnable demo in the repo does exactly this: the agent re-derives a k-eff for itself, then, handed a validly-signed record whose number has been forged, its reproduce check catches the lie and it refuses — trust riding on the re-run, not on a signature alone. (demo/agent_checks_a_record.py.)

One process, one port

The REST API and MCP tools served from a single stdlib HTTP process on port 8765 — no web framework to wire or patch. Localhost-bound; free capabilities are open, Pro capabilities gated by an offline Bearer license token. Pure Python standard library, so nothing to install and nothing to wire together.

MCP tool catalog

Public capabilities are exposed as MCP tools over real JSON-RPC 2.0 (initialize / tools/list / tools/call). Browse the catalog over HTTP, or call the same tools from your own agent or notebook — each call returns the same signed evidence bundle as the REST path, so an agent can verify and reproduce what it gets back instead of trusting a number.

Air-gap by design

No CDN runtime fetches. No telemetry. Nothing phones home — bound to localhost (127.0.0.1), with Pro capabilities gated by an offline license token. Pure Python standard library, so it runs behind any firewall, in a SCIF, or on a laptop with no network at all.

FAQ

What is SMRFORGE?
SMRFORGE is a verifiable platform for Small Modular Reactor (SMR) design and analysis. The free open core (MIT) is the full screening reactor-physics engine: full-core Cartesian nodal diffusion, higher-order NEM (1-D/2-D/3-D) with ADF/SPH equivalence, few-group homogenization, an in-tree continuous-energy Monte Carlo, Sn transport, SP3, burnup/depletion, kinetics and reactivity coefficients, rod-worth, shutdown-margin, pin-power, and xenon/samarium — every result a reproducible evidence bundle, honestly labeled for fidelity. Its Pro tier (FSL-1.1-MIT) adds the assurance layer regulators read: the signed assess deliverable with a PASS/FAIL verdict against the safety floor, plus coverage / freshness / signed-report cards and support — requirements-to-evidence traceability, SRP-section mapping, and a hosted reviewer console are on the roadmap (all physics fidelity — including advanced geometry and full-core CMFD — is free open core; Serpent/MCNP converters are on engagement). Screen fast in pure Python, then escalate the same inputs to a lab-grade Monte Carlo code (OpenMC, free) for reference accuracy. Every run ships as a verifiable evidence bundle.
What's the difference between Community and Pro?
The free open core is MIT-licensed and is the whole screening engine: full-core Cartesian nodal diffusion, higher-order NEM (1-D/2-D/3-D) with ADF/SPH equivalence, continuous-energy Monte Carlo, Sn transport, SP3, burnup/depletion, kinetics and reactivity coefficients, rod-worth, shutdown-margin, pin-power, an OpenMC escalation path, and the full evidence spine (sealed bundles, standalone verifier, verifiable redaction, and data-library provenance). Full-core CMFD, R-Z (cylindrical) diffusion, and the IAEA-2D full-core closure ship free in the open core today; hex geometry is on the open-core roadmap. Pro adds the assurance / regulatory layer: the signed assess deliverable with a PASS/FAIL verdict against the safety floor, plus coverage / freshness / signed-report cards and support; requirements-to-evidence traceability, SRP-section mapping, and a hosted reviewer console are on the roadmap. Converters that generate input decks for — and read results from — your own licensed Serpent and MCNP installations (SMRFORGE does not include or distribute those export-controlled codes) are available on engagement.
Does SMRFORGE include Serpent or MCNP?
No. Serpent and MCNP are third-party codes with their own licenses — MCNP is export-controlled (distributed via RSICC) and Serpent is license-restricted (via VTT / OECD-NEA). SMRFORGE does not contain, bundle, or distribute them, or their nuclear-data libraries. Pro can provide, on engagement,converters that generate input decks for, and read results from, a copy you license and install yourself. OpenMC (open source) is included as the built-in escalation path.
How does SMRFORGE handle reproducibility?
Every run produces an evidence bundle: a SHA-256 manifest of inputs and outputs, a reproducibility block (engine and code version, the nuclear-data library it read and its SHA-256, the RNG seed, and a determinism statement, plus an unsigned host diagnostic (Python version, platform) outside the seal), and a derivation lineage for composed results. smrforge verify <bundle> confirms or refutes a bundle's integrity offline — it checks the record is intact, complete, and untampered against the open schema (integrity), with a checker that imports none of our physics. Re-running the result end-to-end is a separate, deeper step: smrforge reproduce <bundle> re-runs the open engine on the bundle's own recorded inputs and checks the numbers re-derive (the certify_bundle / reproduce_bundle Python API is the same path). A stochastic result (a Monte Carlo k-eff) can't re-derive to the last digit, so its record carries a statistical reproduce_tolerance — an n-sigma band from the run's own reported uncertainty — and reproduce accepts a re-run inside it; that tolerance is sealed in the record, so it can't be quietly widened. A lab-grade OpenMC criticality result reproduces the same way — a reviewer re-runs OpenMC on the recorded inputs and the k re-derives within its band (code-to-code against OpenMC, not a measured-reactor validation).
Is SMRFORGE Pro suitable for licensing-relevant work?
Pro adds the assurance / regulatory layer: the signed assess deliverable — a real reference solve plus a tech-spec shutdown-margin gate in one bundle, with a PASS/FAIL verdict against the safety floor — plus coverage (USL / c_k trending), a freshness monitor, signed shareable evidence reports, and support; requirements-to-evidence traceability, report artifacts mapped to standard SRP sections, and a hosted reviewer console are on the roadmap. The open core ships the same evidence-bundle plumbing — Pro adds the assessment, those cards, and the support contract.
Does SMRFORGE run air-gapped?
Yes. The open core is pure Python standard library with zero dependencies and no CDN fetches at runtime, so it runs fully offline — on a laptop with no internet, in a SCIF, or behind an enterprise firewall. Air-gapped deployment bundles for regulated environments are on the Pro roadmap.
What Python version is required?
Python 3.11 or higher.
How do I install SMRFORGE today?
The open core is open source (MIT) and public now at gitlab.com/smrforge/smrforge. It is not yet on PyPI, so you install from source: git clone the repo, then pip install -e . (Python 3.11+, pure Python standard library, zero dependencies). Today the CLI ships smrforge verify <bundle>, smrforge reproduce <bundle>, smrforge license, and smrforge --version; the rest of the engine is used as a Python API. Also public: the Evidence Envelope standard, its reference verifier (which independently verifies a bundle with its own Ed25519 — no SMRFORGE import), and the reviewer kit (which reproduces a real bundle end-to-end against the pinned engine). The Pro tier is source-available (FSL-1.1) and licensed, in commercial beta; email us for Pro or a pilot. A package-manager-friendly pip install distribution is on the roadmap.
Is there a REST / MCP server?
A single stdlib HTTP surface (smrf_serve) fronts the REST API and the MCP tool catalog as a Python API today — no web framework, no CDN runtime fetches, so it works in fully air-gapped environments. There is no console command for it yet; a serve command is on the roadmap.
