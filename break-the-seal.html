The challenge

Try it in 60 seconds.

One file to read, one record to attack, one key to cross-check. Everything runs on your machine, with nothing of ours imported.

Step 1

Get the verifier

A single standard-library-only file you can read in full.

$ curl -O https://gitlab.com/smrforge/evidence-verifier/-/raw/v0.3.8/evidence_verify.py
Step 2

Get the sealed record

The exact bundle shown above, frozen at cise-v3.

$ curl -O https://gitlab.com/smrforge/smrforge/-/raw/cise-v3/packs/openmc-criticality.reproduce-demo.bundle.json
Step 3

Cross-check our key

The fingerprint the verifier prints must match smrforge.io/.well-known/smrforge-trust-root and the DNS TXT record smrforge-trust-root.smrforge.io. Two channels, neither of them the verifier itself.

Step 4

Run it, then beat it

$ python evidence_verify.py verify openmc-criticality.reproduce-demo.bundle.json

It passes. Change k_eff to a different value and run again: it fails and names the broken section. Your challenge is to make an edited copy it still reports as signed by our key.

The rules

What counts as a break.

The verifier’s own printed verdict is the judge. Move the value, keep the pass, under our pinned key. Everything else is a shortcut we already closed.

The break

A different number, still signed by us.

Using the unmodified public verifier, pinned to our production key (fingerprint cross-checked from the two channels above), produce a record whose k_eff is a genuinely different value from 1.00522 and that the verifier still reports as a pass signed by the pinned key.

Does not count

The same number written differently.

1.0052200 is the same value as 1.00522; the verifier re-derives the number before hashing, so a reformat is not a changed result. A break has to move the value.

Does not count

Editing the verifier.

Run it unchanged; you can read every line. The key is pinned and cross-checkable from two channels precisely so a swapped verifier cannot help.

Does not count

An unsigned or differently-signed record.

The verifier fails any record that is unsigned or signed by any key other than our pinned production key. That is not a pass under our key.

Does not count here

Breaking Ed25519 or SHA-256 itself.

If you can do that, you have earned a far larger prize and should tell the world, not us.

The interesting break

A flaw in the verifier or the format.

A record whose asserted result genuinely differs yet still passes. If you find one, report it responsibly and it gets fixed in a release that names you.

Forge the signature

Tell us, and the world.

If you produce a record our pinned key verifies with the number changed, that is a result of cryptographic significance.

A break is

  • An unmodified-verifier pass, under our pinned key, on a record whose k_eff is a genuinely different value.
  • A verifier or format flaw: a record with a different asserted result that still passes.

A break is not

  • Editing the verifier.
  • The same number rewritten in another form.
  • An unsigned or other-key record (the verifier fails it).
  • Breaking Ed25519 or SHA-256.

Honest boundary

What this proves, and what it does not.

This challenge is about custody: whether a computed number can be quietly changed or forged on its way to a reviewer. It cannot. Whether the number is right is a different question.

Custody, not correctness. A pass proves the record is unaltered, signed by SMRFORGE, and that the number re-derives from the sealed inputs. It does not prove the number is physically correct. The sealed value is an OpenMC multi-group eigenvalue on a homogeneous slab, advisory and lab-escalation grade; continuous energy and heterogeneous geometry are the next escalation, and whether 1.00522 is the right answer is a validation question, settled against experiment and the adequacy frameworks that govern reactor analysis.

Verification (the seal holds, the number re-derives) is not validation (the number matches a measured experiment). SMRFORGE results are screening-to-reference grade and advisory, labeled on every result. Nuclear data cited on this site is openly distributable (ENDF/B-VIII.0 and VIII.1).
