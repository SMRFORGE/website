How trust is built

Five steps. Each one ends in an artifact you can check.

Accuracy claims are universal. SMRFORGE ships, with every result, the process that would catch a wrong number — and the record that lets an independent reviewer confirm it without taking our word for anything.

1

Fidelity declaration

Every result carries a machine-readable fidelity label — screening, reference, or lab-escalation — stated in the output record itself.

2

Residual quantification

Validation is reported per benchmark with published error bands — e.g. TMI-1 −24 ± 121 pcm and lattice-to-core ≈1 pcm (LWR and method anchors) — with open items tracked in a public V&V matrix.

3

Cryptographic sealing

Each run is committed to a tamper-evident bundle — a SHA-256 manifest of every input, output, and software version; any alteration breaks the seal.

4

Transparency logging

Bundle digests can be committed to an append-only, RFC 6962-style Merkle log; inclusion and consistency proofs check offline. (A hosted public log is on the roadmap.)

5

Independent verification

A standalone verifier confirms a record's integrity — unedited, and consistent with the open Evidence Envelope schema — offline, with any conformant verifier, including one you implement yourself.

Validated closure-by-closure — error bars published

We state validation closure-by-closure, with published bands — and we publish where the methods don't agree, too.

An honest starting point: there are almost no measured SMR benchmarks yet — most SMRs aren't operating — so, like the whole field, we validate the method against the best-characterized data that exists. We anchor it on well-known references: lattice-to-core reactivity holds to about 1 pcm (a code-verification result, figure below), and on the measured TMI-1 HZP pin cell our continuous-energy engine agrees with an OpenMC ENDF/B-VIII.0 reference to −24 ± 121 pcm (within ±200). Then — the part that matters for your SMR — the same inputs for any archetype escalate to OpenMC, free for everyone, so you get a code-to-code check on your actual design, not just on a legacy core. Those references are LWR and method anchors, not SMR-specific validation — and we say so. Every result is a bundle you re-verify offline; what Pro adds is the assurance layer that turns the numbers into a regulatory submission.

Built for simulations you can defend

Reproducibility is the product, not a feature.

Every k-eff calc, every benchmark, every report ships as a verifiable evidence bundle. A SHA-256 manifest of inputs and outputs. A reproducibility block — engine and code version, the ENDF library and its SHA-256, the RNG seed, a determinism statement, and the host Python version. A schema-versioned audit trail of every action that produced the result.

Hand the bundle to a colleague, a reviewer, or a regulator. They run a standalone verifier offline and either confirm the record's integrity — unedited and schema-valid — or refute it, checked against the open, independently-implementable Evidence Envelope schema (a versioned spec, JSON Schema, and conformance vectors), not a SMRFORGE-proprietary format. No "trust me, it ran on my machine." (Re-running the physics end-to-end is a separate, deeper check: smrforge reproduce <bundle> re-runs the open engine on the bundle's own recorded inputs and checks the numbers re-derive — the certify_bundle / reproduce_bundle Python API is the same path.) The published conformance vectors let you certify any verifier — ours or one you wrote yourself — so "independently-implementable" is something you prove, not something we ask you to take on faith.

Evidence bundles

Versioned, hashable, schema-checked. The same evidence plumbing internally is what regulators and reviewers receive — no separate export pipeline to maintain.

Air-gap by construction

Pure Python standard library, zero dependencies, zero CDN fetches at runtime. Works on a laptop with no internet, in a SCIF, or behind an enterprise firewall. The archetype presets ship a screening cross-section set in-tree — no nuclear-data download is required to reach a k-effective number. Advanced ENDF-driven workflows stage their data separately; Pro adds verified air-gapped deployment bundles for those.

Locked surface, gated drift

300+ tests, golden snapshots, and published conformance vectors — run them yourself against any build. A determinism check guards bit-reproducibility. (A hosted CI gate is on the roadmap; today the checks are yours to run.)

Append-only transparency log

Bundle digests can be committed to an RFC 6962-style Merkle log. From a tree head, anyone pulls an inclusion proof — your record is in the log — or a consistency proof — the log was only appended to, never rewritten — and checks it offline with a stdlib verifier, no trust in whoever runs the log. A hosted public log that publishes signed tree heads is on the roadmap.

One gateway, every surface

API + AI tools — one process you can audit.

The SMRFORGE gateway is a single stdlib HTTP surface — no web framework — that fronts the REST API and the MCP tool catalog your AI agents can call. One process, one port, one OpenAPI spec, one audit log. Today it is a Python API (smrf_serve) you start in-process; a serve console command is on the roadmap.

MCP tool catalog

Audit log + air-gap by design

FAQ

What is SMRFORGE?
SMRFORGE is a verifiable platform for Small Modular Reactor (SMR) design and analysis. The free open core (MIT) is the full screening reactor-physics engine: full-core Cartesian nodal diffusion, higher-order NEM (1-D/2-D/3-D) with ADF/SPH equivalence, few-group homogenization, an in-tree continuous-energy Monte Carlo, Sn transport, SP3, burnup/depletion, kinetics and reactivity coefficients, rod-worth, shutdown-margin, pin-power, and xenon/samarium — every result a reproducible evidence bundle, honestly labeled for fidelity. Its Pro tier (FSL-1.1-MIT) adds the assurance layer regulators read: the signed assess deliverable with a PASS/FAIL verdict against the safety floor, traceability, report artifacts, a reviewer console, and support (all physics fidelity — including advanced geometry and full-core CMFD — is free open core; Serpent/MCNP converters are on engagement). Screen fast in pure Python, then escalate the same inputs to a lab-grade Monte Carlo code (OpenMC, free) for reference accuracy. Every run ships as a verifiable evidence bundle.
What's the difference between Community and Pro?
The free open core is MIT-licensed and is the whole screening engine: full-core Cartesian nodal diffusion, higher-order NEM (1-D/2-D/3-D) with ADF/SPH equivalence, continuous-energy Monte Carlo, Sn transport, SP3, burnup/depletion, kinetics and reactivity coefficients, rod-worth, shutdown-margin, pin-power, an OpenMC escalation path, and the full evidence spine (sealed bundles, standalone verifier, RFC-6962 transparency log). Full-core CMFD, R-Z (cylindrical) diffusion, and the IAEA-2D full-core closure ship free in the open core today; hex geometry is on the open-core roadmap. Pro adds the assurance / regulatory layer: the signed assess deliverable with a PASS/FAIL verdict against the safety floor, requirements-to-evidence traceability, SRP-aligned report artifacts, a reviewer console, and support. Converters that generate input decks for — and read results from — your own licensed Serpent and MCNP installations (SMRFORGE does not include or distribute those export-controlled codes) are available on engagement.
Does SMRFORGE include Serpent or MCNP?
No. Serpent and MCNP are third-party codes with their own licenses — MCNP is export-controlled (distributed via RSICC) and Serpent is license-restricted (via VTT / OECD-NEA). SMRFORGE does not contain, bundle, or distribute them, or their nuclear-data libraries. Pro ships converters that generate input decks for, and read results from, a copy you license and install yourself. OpenMC (open source) is included as the built-in escalation path.
How does SMRFORGE handle reproducibility?
Every run produces an evidence bundle: a SHA-256 manifest of inputs and outputs, a reproducibility block (engine and code version, the ENDF library and its SHA-256, the RNG seed, a determinism statement, and the host Python version), and a schema-versioned audit trail. smrforge verify <bundle> confirms or refutes a bundle's integrity offline — it checks the record is intact, complete, and untampered against the open schema (integrity), without the tool that produced it. Re-running the result end-to-end is a separate, deeper step: smrforge reproduce <bundle> re-runs the open engine on the bundle's own recorded inputs and checks the numbers re-derive (the certify_bundle / reproduce_bundle Python API is the same path).
Is SMRFORGE Pro suitable for licensing-relevant work?
Pro adds the assurance / regulatory layer: the signed assess deliverable — a real reference solve plus a tech-spec shutdown-margin gate in one bundle, with a PASS/FAIL verdict against the safety floor — automated requirements-to-evidence traceability, report artifacts that map to standard SRP sections, a reviewer console, and support. The open core ships the same evidence-bundle plumbing — Pro adds the assessment, the templates, the workflows, and the support contract.
Does SMRFORGE run air-gapped?
Yes. The open core is pure Python standard library with zero dependencies and no CDN fetches at runtime, so it runs fully offline — on a laptop with no internet, in a SCIF, or behind an enterprise firewall. Pro adds verifiable air-gapped deployment bundles for regulated environments without internet access.
What Python version is required?
Python 3.11 or higher.
How do I install SMRFORGE today?
The open core is open source (MIT) and public now at gitlab.com/smrforge/smrforge. It is not yet on PyPI, so you install from source: git clone the repo, then pip install -e . (Python 3.11+, pure Python standard library, zero dependencies). Today the CLI ships smrforge verify <bundle>, smrforge reproduce <bundle>, smrforge license, and smrforge --version; the rest of the engine is used as a Python API. Also public: the Evidence Envelope standard, its reference verifier (which independently verifies a bundle with its own Ed25519 — no SMRFORGE import), and the reviewer kit (which reproduces a real bundle end-to-end against the pinned engine). The Pro tier is source-available (FSL-1.1) and licensed, in commercial beta; email us for Pro or a pilot. A package-manager-friendly pip install distribution is on the roadmap.
Is there a REST / MCP server?
A single stdlib HTTP surface (smrf_serve) fronts the REST API and the MCP tool catalog as a Python API today — no web framework, no CDN runtime fetches, so it works in fully air-gapped environments. There is no console command for it yet; a serve command is on the roadmap.
