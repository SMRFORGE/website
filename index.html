How you check it

Three ways to catch us. All on your machine.

Integrity is one command. Re-deriving the number is a deeper one. Walking a derivation is a third. None needs a network, and none trusts us.

$ smrforge verify <bundle>

Verify offline

A standalone checker confirms the record is intact, complete and signed, and it imports none of our physics, so a pass isn’t us grading our own work. The in-browser version is a from-scratch RFC 8032 Ed25519 verifier with no crypto library behind it. Run it on a real bundle.

$ smrforge reproduce <bundle>

Reproduce the number

A signature can’t catch a signed lie. This re-runs the open engine on the bundle’s own recorded inputs and checks the number comes back: exact for deterministic solvers, within the sealed band for Monte Carlo.

$ smrforge verify --chain <bundle> --from <dir>

Walk the derivation

A result built from another sealed result cites it by content hash. The walker checks every link offline, from the upstream constants to the final number, with the upstream bundles you hand it. Custody, end to end.

Sealed cross-bundle chaining

A number that remembers where it came from.

Every bundle pins its inputs and outputs by SHA-256, names the nuclear data it read by content hash, and seals the toolchain that minted it, machine and solver. When one sealed result feeds the next, the downstream bundle binds the upstream by hash in a sealed derived_from link. Alter anything upstream and the chain breaks where it was altered.

A link carries facts, never a verdict.

The sealed link holds digests of what was consumed. Whether the chain is sound is decided by the verifier that walks it, on your machine, every time. No bundle gets to grade its own upstream.

Re-run the cheap step, not the whole pipeline.

With the upstream constants sealed and verified, a reviewer can re-derive the deterministic step on them directly, without repeating the expensive calculation that produced them.

Binding, not decoration.

The consumed value sits in the downstream bundle’s own sealed inputs and is pinned to the upstream seal, so a swapped upstream, a laundered key, or an edited constant each fail where they were touched.

Any computation, one seal

The seal doesn’t care what the number is.

A bundle seals whatever the computation outputs. Inputs, result, provenance, one SHA-256 manifest, one Ed25519 signature. A single k_eff is the easiest thing to show, so it is the demo, and a full-core flux map ships sealed the same way. The same record is built to hold a depletion curve, a rod-worth table or a USL margin, with no change to how it is sealed or checked.

Install
$ git clone https://gitlab.com/smrforge/smrforge.git && cd smrforge && pip install -e .

Source-only, by design. Python 3.11+, pure standard library, no dependencies. It is not on PyPI, on purpose: the engine is built for air-gapped and regulated environments, so what you install is the source tree you can read, never a package index. Getting started →

$ smrforge run physics:nodal --preset lwr-smr-2g --enrichment-pct 4.5 --core-size-cm 200

Command line

One flag per declared input. smrforge tools lists the open capabilities and smrforge schema <card> prints one card’s inputs; a missing or misspelled input is a named error, not a stack trace. The output is a sealed evidence bundle.

run_capability("physics:nodal", inputs)

Python

Register the open cards, call run_capability(name, inputs), and get the result and the same sealed bundle back: the same input checks, the same record.

$ smrforge serve

REST + MCP, on your machine

A standard-library HTTP server bound to 127.0.0.1. POST a JSON body to run a card and the response is the bundle; the same server speaks MCP to an AI agent. No web framework, no network fetches.

What runs where. The in-tree engine runs anywhere Python does. The lab-grade OpenMC path needs a real OpenMC install and a continuous-energy cross-section library on your host; without them those cards refuse, rather than fabricate a number.

Questions

The short answers.

Longer ones on the info sheet and in the open repository.

What is SMRFORGE?
The evidence layer for reactor physics. The free open core (MIT) is a screening-grade reactor-physics engine, full-core nodal diffusion and NEM through an in-tree continuous-energy Monte Carlo, with one-step escalation to OpenMC. Every result becomes a sealed evidence bundle anyone can verify offline and re-derive by re-running the open engine on its recorded inputs. Pro (FSL-1.1-MIT) adds the assurance layer a regulator reads. Physics is free and stays free; Pro is never physics.
What does the seal prove, and what doesn’t it?
Custody: the number in front of you is the number the engine produced, nothing altered it, and the run can be re-derived from the inputs in the bundle. Under our pinned production key it also proves origin. It does not prove the physics is right; a sealed number from a badly specified core is a faithfully preserved wrong answer. Results are screening-to-reference grade and advisory, labeled on every result. Nobody should license a reactor on a SMRFORGE number alone.
How do reproducibility and chaining work?
Every bundle carries a SHA-256 manifest of inputs and outputs, a reproducibility block (engine version, the nuclear-data library by content hash, the RNG seed, a determinism statement, and the minting toolchain: machine and solver), and a derivation lineage. smrforge verify checks integrity offline with a checker that imports none of our physics. smrforge reproduce re-runs the open engine on the bundle’s own inputs. When a result was built from another sealed result, its bundle binds the upstream by hash in a sealed derived_from link, and smrforge verify --chain <bundle> --from <dir> walks every link offline. The link carries facts, never a verdict: the verifier that walks the chain decides.
What’s the difference between Community and Pro?
Community (MIT) is the whole screening engine and the whole evidence spine: nodal diffusion and NEM, SN/SP3, continuous-energy Monte Carlo, the OpenMC escalation path, sealed bundles, the standalone verifier, reproduce, chain walking, verifiable redaction, and data-library and toolchain provenance. Pro (FSL-1.1-MIT) adds the assurance layer: the signed assess deliverable with a PASS/FAIL verdict against the safety floor, chained to the sealed reference bundle it consumed; coverage; watch; signed reports with lineage; the Evidence Console; and support.
Does SMRFORGE run air-gapped?
Yes. The open core is pure Python standard library with zero dependencies and no network fetches at runtime, so it runs fully offline: a laptop with no internet, a SCIF, an enterprise firewall. The verifier, reproduce, and the chain walker are all offline; the walker takes upstream bundles from a directory or archive you supply, never from a network.
How do I install it?
From source, at gitlab.com/smrforge/smrforge: clone, then pip install -e . (Python 3.11+). Not on PyPI, by design. Also public: the Evidence Envelope standard, its single-file reference verifier with no SMRFORGE import, and the reviewer kit. Pro is source-available (FSL-1.1) and licensed, in commercial beta.
Is there a REST / MCP server?
Yes. smrforge serve starts a standard-library HTTP server on 127.0.0.1 (port 8765 by default) fronting a REST API (POST /v1/run/<capability> returns the signed bundle; /v1/tools and /openapi.json describe it) and an MCP endpoint (JSON-RPC 2.0 at /mcp) for AI agents. No web framework, no network fetches. Pro cards are not served by the open server; they need an entitlement token.
