The challenge

Try it in 60 seconds

  1. Get the verifier, a single standard-library-only file you can read in full: curl -O https://gitlab.com/smrforge/evidence-verifier/-/raw/v0.3.2/evidence_verify.py
  2. Get the sealed record: curl -O https://gitlab.com/smrforge/smrforge/-/raw/cise-v1/packs/openmc-criticality.reproduce-demo.bundle.json
  3. Cross-check our key out of band. The fingerprint the verifier prints must match smrforge.io/.well-known/smrforge-trust-root and the DNS TXT record smrforge-trust-root.smrforge.io.
  4. Run it, then try to beat it: python evidence_verify.py verify openmc-criticality.reproduce-demo.bundle.json It passes. Change k_eff to a different value and run again: it fails and names the broken section. Your challenge is to make an edited copy it still reports as signed by our key.

These refs are frozen: the record at cise-v1 (commit ca52239), the verifier at v0.3.2 (commit f5e31fc). The record's integrity rests on its signature, not the URL, so bytes served under any other name simply fail to verify.

Prefer zero install? The same verifier runs live on the Check a bundle page, on this exact record. Change a digit and watch the seal catch it, no download required.

The rules

What counts as a break

  • Using the unmodified public verifier, pinned to our production key (fingerprint cross-checked from the two channels above), produce a record whose k_eff is a genuinely different value from 1.00522 and that the verifier still reports as a pass signed by the pinned key. The verifier's own printed verdict is the judge.
  • The same number written differently does not count. 1.0052200 is the same value as 1.00522; the verifier re-derives the number before hashing, so a reformat is not a changed result. A break has to move the value.
  • Editing the verifier does not count. Run it unchanged; you can read every line. The key is pinned and cross-checkable from two channels precisely so a swapped verifier cannot help.
  • An unsigned or differently-signed record does not count. The verifier fails any record that is unsigned or signed by any key other than our pinned production key. That is not a pass under our key.
  • Breaking Ed25519 or SHA-256 itself does not count here. If you can do that, you have earned a far larger prize and should tell the world, not us.
  • The interesting break is a flaw in the verifier or the format: a record whose asserted result genuinely differs yet still passes. If you find one, report it responsibly below.

A break is

  • An unmodified-verifier pass, under our pinned key, on a record whose k_eff is a genuinely different value.
  • A verifier or format flaw: a record with a different asserted result that still passes.

A break is not

  • Editing the verifier.
  • The same number rewritten in another form.
  • An unsigned or other-key record (the verifier fails it).
  • Breaking Ed25519 or SHA-256.

Honest boundary

What this proves, and what it does not

A pass proves the record is unaltered, signed by SMRFORGE, and that the number re-derives from the sealed inputs. It does not prove the number is physically correct. The sealed value is an OpenMC multi-group eigenvalue on a homogeneous slab, advisory and lab-escalation grade; continuous energy and heterogeneous geometry are the next escalation, and whether 1.00522 is the right answer is a validation question, settled against experiment and the adequacy frameworks that govern reactor analysis. This challenge is about custody: whether a computed number can be quietly changed or forged on its way to a reviewer. It cannot.
