I rolled my own Ed25519 verifier for my reactor-physics results

In Python, standard library only, no libsodium. Go ahead and tell me that's how you get owned, then try to break it, because I'm daring you to.

SMRFORGE · reactor physics you can prove

Here's why I did something that stupid-sounding on purpose.

I build reactor-physics software for small modular reactors (SMRFORGE, MIT). A result from it is a number, a k-effective or a shutdown margin, and when one lands on someone's desk today, they have no mechanical way to tell where it came from or whether it was altered on the way. Which nuclear data? Which method? Which inputs? The PDF doesn't say. If a script or a model touched it en route, it could have been changed and nothing would show. You trust the producer because there's no alternative. I find that unacceptable, so I built the alternative.

The core idea: separate custody from correctness. Correctness, meaning is the number physically right, is a judgment that needs an expert and should stay one. Custody, meaning is this the exact number the solver produced with these inputs and this data, unaltered, is a yes/no question that should never require trusting anyone. Today it does. That's the gap.

So every result ships as an “evidence bundle”: canonical JSON with the result, inputs, and provenance, a SHA-256 manifest over each section, and an Ed25519 signature over the manifest. Verify = recompute each digest, check the manifest, check the signature. Change one digit and that section's digest stops matching what was signed; the check fails and names the section. The math catches the edit, not me.

Now, the verifier. From scratch, stdlib only, because the whole trust path then fits in one file you can read top to bottom and run with the network cable pulled. That's the entire point in air-gapped, regulated environments. Yes, rolling your own EdDSA is the canonical mistake. The honest part: I got it wrong at first. My early version used the cofactorless equation but didn't reject small-order points or the non-canonical x=0 encoding, so it accepted signatures it never should have. I caught it running “Taming the Many EdDSAs”-style vectors against my own code, added the verify_strict-style rejections (small-order A and R, s>=L, the 5.1.3 x=0 rule), and published the known-answer vectors. Browser, single-file, and CLI verifiers all agree on them. Make mine disagree with libsodium or ref10 on a single vector and you've made my week.

Try it in sixty seconds: a page verifies a real signed bundle in your browser (the Ed25519 check runs client-side), then lets you edit a digit and watch it fail. Want to check your own bundle? One stdlib file, no install. Want to go past custody? The engine is open: re-run the sealed inputs and see the number come back. A signature can't catch a signed lie; re-running can.

I'll state the limits first, because overselling this is the fastest way to get it torn apart. The seal proves custody, not correctness. A sealed k-eff from a garbage model is a faithfully preserved wrong answer. Benchmark checks on open ENDF/B-VIII data are code verification, not validation against experiment. Results are screening-grade and advisory. Do not license a reactor on one. What I claim is narrow and I mean it narrowly: you can check, yourself, offline, that a number is the one that was produced and that you can re-derive it. Nobody could, before.

And the dare, since I opened with it: I've published a signed result and the verifier that checks it. Change the number, get it past the verifier. Nobody has. Don't trust me. Break me.
